# تقرير التحقق النهائي — 4.49.21

**التاريخ:** 2026-11-18 | **الفرع:** `main` | **الإصدار:** `4.49.21` |
**الالتزام الأساسي عند بدء العمل:** `95a6836` (الإصدار 4.49.20) |
**بيئة التحقق:** Python 3.12.3 على Linux، البيئة الافتراضية نفسها من 4.49.20
(pytest 9.1.1، ruff 0.17.3)

## ما أُصلح

- **فشل CI على Windows وحدها:** بعد دفع 4.49.20 فشل GitHub Actions
  (تشغيل 44228359296 والتشغيل السابق له) على `windows-latest` فقط
  (Python 3.12 و3.14) بينما نجح `ubuntu-latest`، ونجحت خطوات `ruff`
  و`compileall` و`pip check` على Windows أيضاً. الخطوة الفاشلة كانت
  الاختبارات (`python -m pytest -q --tb=short`، رمز خروج 1).
- **السبب — اختبار واحد:** `test_doctor_permission_check_uses_app_directory`
  في `tests/test_hardening_44920.py` كان يتوقع تحذير WARN لملف
  `account_token.json` بأذونات واسعة، لكن قسم فحص الأذونات 7.5 في
  `doctor.py` محروس قصداً بـ `if os.name == "posix"` — Windows بلا أوضاع
  chmod، فالقسم لا يعمل هناك أصلاً ولا يظهر أي WARN. أُثبت ذلك بمحاكاة
  Windows محلياً (انظر «محاكاة Windows» أدناه): الاختبار يفشل بـ
  `AssertionError` صريح عند `assert any(status == doctor.WARN ...)`
  عندما يكون `os.name == "nt"`.
- **الإصلاح:** الاختبار صار يُتخطَّى على غير POSIX
  (`@pytest.mark.skipif(os.name != "posix", reason="فحص أذونات الملفات POSIX فقط")`)
  كما في اختبارات الأذونات الأخرى (`test_hardening_449.py`،
  `test_v413_features.py`، `test_v413_hardening.py`)، دون أي تغيير في
  كود الإنتاج ودون إضعاف فحص الأذونات أو تزييف WARN على Windows.
- **اختبار جديد:** `test_doctor_permission_check_is_posix_only` يحاكي
  Windows (`os.name = "nt"`) ويثبت أن `_collect_checks` لا يُنتج تحذير
  أذونات هناك — أي أن هذا سلوك مقصود لا عطلاً، حتى لا يُعاد إدخال
  اختبار يفترض WARN على Windows.

## محاكاة Windows

سجلات CI التفصيلية تتطلب تسجيل دخول GitHub ولم تكن متاحة؛ أُعيد إنتاج
الفشل محلياً بمحاكاة Windows لكل اختبار على حدة (`os.name = "nt"` أثناء
جسم الاختبار فقط، مع `os.O_TEMPORARY` و`pathlib.WindowsPath` كما في
مفسر Windows الحقيقي — فـ `tempfile` و`pathlib` يقرآن `os.name` عند
الاستدعاء، وبدون هذين التصحيحين تنهار المحاكاة نفسها بأخطاء وهمية).

- **اختبارات الملف الـ13 تحت المحاكاة:** 12 ناجحة، وفشل واحد فقط —
  اختبار doctor للأذونات (`AssertionError` عند تأكيد WARN). هذا الفشل
  متوقَّع في المحاكاة نفسها لأنها تستدعي الدالة مباشرة متجاوزةً تقييم
  `skipif`؛ على Windows الحقيقي يُقيَّم الشرط عند الاستيراد فيُتخطَّى
  الاختبار (أُثبت أدناه).
- **كامل المجموعة تحت المحاكاة:** 712 ناجحة و4 فاشلة واختباران
  متخطيان (718 اختباراً). الأربعة الفاشلة كلها اختبارات أذونات تُتخطَّى
  على Windows الحقيقي: اختبار doctor هذا، وثلاثة اختبارات قديمة
  (`test_secure_log_handler_creates_file_private_from_the_start`،
  واختبارا `test_harden_secret_file_restricts_permissions` في
  `test_v413_features.py` و`test_v413_hardening.py`) محروسة بـ
  `skipif(os.name != "posix")` أصلاً — والمحاكاة تقيّم `skipif` عند
  الاستيراد تحت POSIX فتشغّلها، وهذا قيد في المحاكاة لا انحدار.
- **إثبات التخطّي:** باستيراد ملف الاختبار بعد ترقيع `os.name` إلى
  `"nt"` (بعد استيراد وحدات التطبيق مسبقاً) كان شرط `skipif` للاختبار
  `True` مع السبب «فحص أذونات الملفات POSIX فقط» — أي أن الاختبار
  سيُتخطَّى فعلاً في تشغيل Windows CI.
- لم يُعثر على عطل إنتاج آخر خاص بـ Windows في كود 4.49.20: اختبارات
  `diagnostic_report` (مهلة DNS بالخيوط) و`upload_pipeline` (الجدولة)
  و`facebook_scraper` (DoH) و`_facebook_watch_og_title` (حارس SSRF)
  و`enable_automation.show_status` كلها ناجحة تحت المحاكاة.

## نتائج التحقق

- **الاختبارات:** نجحت مجموعة `pytest` كاملة: **716 اختباراً**،
  واختباران متخطيان (`tests/test_hardening_4491.py:91` و`:132`) يتطلبان
  دلالات أذونات POSIX ولا يعملان عند التشغيل كـ root. الأساس قبل
  التغيير كان 715 اختباراً ناجحاً واختبارين متخطيين؛ أُضيف اختبار
  محاكاة Windows واحد في `tests/test_hardening_44920.py` (صار فيها 13
  اختباراً)، واختبار doctor للأذونات يُتخطَّى الآن على Windows قصداً.
- **فحص الشيفرة:** نجح `ruff check .` بلا ملاحظات.
- **التجميع:** نجح `python -m compileall -q .` (باستثناء `.venv` و`.git`).
- **الإصدار:** يعرض `--version` الإصدار `4.49.21`، ورقم الإصدار متسق
  في `version.py` وترويسة الملف الرئيسي و`README.md` و`AGENTS.md`
  (يثبّتها `test_version_44921_consistent_everywhere`).
- **بوابة الحقوق لم تتغير:** الوضع الافتراضي `strict` مع المراجعة
  اليدوية قبل كل رفع. لا رفع حي ولا تسجيل دخول إلى Facebook أو
  YouTube في هذا الإصدار.
